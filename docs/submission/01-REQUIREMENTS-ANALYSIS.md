# 01 - Requirements Analysis and Resolved Decisions

## 1. System Overview

Null Portal is a full-stack Secure Examination Management System built for institutions to author, schedule, conduct, monitor, grade, publish, dispute, and verify timed online examinations. The system enforces three application roles:

- **Administrator (`ADMIN`)**: Manages users (create with one-time temporary password, role updates, deactivate/reactivate, admin password reset), views platform statistics, inspects all exams in read-only mode with emergency close/cancel and owner-reassignment controls, audits platform-wide activity (`/admin/audit`), and makes final independent decisions on escalated result disputes (`/admin/disputes`). Cannot author questions, take exams, or grade submissions.
- **Examiner (`EXAMINER`)**: Manages a private topic and question bank (manual CRUD plus CSV/JSON bulk import), authors and configures exams across lifecycle stages (`DRAFT`, `PUBLISHED`, `CLOSED`), enrolls candidates (manual or CSV import with one-time temporary passwords), previews exams in an isolated sandbox, monitors live attempts, posts live announcements, grants audited time extensions, grades written answers (per-candidate or blind grade-by-question), publishes results, runs audited answer-key rescores, resolves candidate disputes, inspects question analytics, and exports summary PDF/CSV reports.
- **Candidate (`CANDIDATE`)**: Self-registers publicly (assigned `CANDIDATE` only), completes pre-exam system checks, takes timed exams with offline resilience, digital scratchpad, and customizable workspace preferences, receives submission receipts, views published results and conditional answer keys, downloads verifiable QR PDF reports, and files or escalates result disputes.

## 2. Requirement Register

Each requirement from the competition brief is classified as `clear`, `unclear`, `incomplete`, `ambiguous`, or `contradictory`, together with the engineering decision taken and its rationale.

| ID | Requirement | Type | Decision | Reason |
|---|---|---|---|---|
| 3.1 | Authentication, RBAC, and User Management | incomplete | Public `/register` creates `CANDIDATE` only; `ADMIN` creates/edits/deactivates users and resets passwords with one-time temporary passwords; JWT `sid` cookie verified against PostgreSQL `users.session_version` and `users.active_session_id` on every request. | Prevents privilege escalation, eliminates SMTP dependency, revokes deactivated/logged-out sessions immediately, and blocks concurrent account sharing (`409 SESSION_ACTIVE`). |
| 3.2 | Question Bank Management | clear | Private per-examiner `topics` and `questions` (`MCQ_SINGLE`, `MCQ_MULTI`, `WRITTEN`) with difficulty and default marks; questions referenced by non-draft exams lock against edits (`409`) and use Duplicate; deletion is soft archive (`archived = true`). | Guarantees historical exam snapshots and analytics never break when the question bank evolves. |
| 3.3 | Examination Creation and Configuration | ambiguous | Stored status is `DRAFT`, `PUBLISHED`, or `CLOSED` (plus `cancelled`); displayed phase (`DRAFT`, `UPCOMING`, `ONGOING`, `COMPLETED`) is derived from PostgreSQL `now()`. Three edit levels (`FULL`, `LIVE`, `TITLE_ONLY`) enforced by `editLevel()`. | Eliminates cron drift and clock skew; allows full edits before any candidate starts while locking fairness-critical settings once live. |
| 3.4 | Candidate Enrollment and Access Control | incomplete | Manual enrollment and two-step CSV import (validate -> commit) with one-time temporary passwords for new accounts; candidate dashboard partitions exams into Available now, Upcoming, and Completed with explicit lock reasons. | Supports realistic institutional onboarding without email infrastructure and prevents unauthorized access to unenrolled exams (`404`). |
| 3.5 | Timed Examination Engine | clear | Transactional attempt start (`ON CONFLICT DO NOTHING` + resume) creates immutable `attempt_questions` snapshot and deterministic Mulberry32 shuffle (`attempts.seed`); client countdown anchors `performance.now()` to `serverNow`; lazy expiry (`finalizeIfExpiredInTx`) runs under `FOR UPDATE`. | Eliminates double-start races, prevents early answer-key leaks, resists device clock tampering, and enforces exact server deadlines. |
| 3.6 | Submission, Auto-Grading, and Manual Grading | ambiguous | Idempotent submit generates `receipt_code`; MCQs auto-grade immediately (`MCQ_SINGLE` optional negative marking `0..1`, `MCQ_MULTI` `PARTIAL` or `ALL_OR_NOTHING`, total clamped `>= 0`); written answers graded manually in `0.5` steps; results publish blocked (`409`) while any real attempt is `NEEDS_REVIEW`. | Guarantees consistent, auditable scores and prevents partial result releases. |
| 3.7 | Live Monitoring and Integrity Controls | ambiguous | 10s candidate heartbeat, 5s examiner monitor polling, live announcements, audited time extensions (`1..120` min + reason), and advisory incident logging (`TAB_HIDDEN`, `WINDOW_BLUR`, `FULLSCREEN_EXIT`, `COPY_PASTE`, `DISCONNECT`, `RECONNECT`, `LATE_SYNC`, `LATE_REJECTED`) explicitly labelled as advisory, never auto-penalizing. | Browser signals cannot prove misconduct; labelling them as advisory supports fair human judgment while audited extensions handle legitimate outages. |
| 3.8 | Results, Reports, and Auditability | clear | Candidate result page with score breakdown, conditional answer key (`show_answers`), CSV export (formula-injection safe), server-side PDF reports, and append-only `audit_log` (PostgreSQL trigger prevents `UPDATE`/`DELETE`). | Ensures transparent reporting and tamper-evident institutional accountability. |
| 4.1 | Network-Aware Interface | clear | `/api/ping` latency and connectivity monitor (`src/lib/use-network-status.ts`) paired with live Save / Offline / Queued status indicators inside the exam workspace. | Gives candidates unambiguous feedback during unstable or offline connections. |
| 4.2 | PDF Report Generation | clear | Server-generated PDFs via `jsPDF` for candidate verifiable result reports (`/api/attempts/[id]/report.pdf`) and examiner exam summaries (`/api/exams/[id]/report.pdf`) with RBAC checks. | Avoids headless-browser runtime dependencies on serverless hosts while using real database data. |
| 4.3 | Examination Sandbox | clear | Examiner launches isolated preview via `POST /api/exams/[id]/sandbox` (`attempts.is_sandbox = true`) with a visible SANDBOX banner and Reset action; `real_attempts` SQL view excludes sandbox rows from all stats, grading, analytics, and reports. | Database-level view isolation eliminates the risk of sandbox data leaking into real results. |
| 4.4 | Bulk Data Import | incomplete | Two-step validate -> row-level error preview -> transactional commit for Questions (CSV/JSON) and Candidates (CSV), rejecting spreadsheet formula prefixes (`=`, `+`, `-`, `@`). Sample files in `public/samples/`. | Prevents partial corrupt imports and neutralizes CSV formula injection at ingestion. |
| 4.5 | Question Analytics | clear | Real-attempts-only Recharts accuracy/skip chart, option distractor distribution, and declared-vs-observed difficulty mismatch flags (`GET /api/exams/[id]/analytics`). | Surfaces poorly calibrated or ambiguous questions without mixing sandbox previews. |
| 4.6 | Verifiable Reports | clear | Public `/verify` lookup and `/verify/[code]` page (linked by QR code on candidate PDF) displaying exam title, masked candidate initials, score/band, issue date, and live status (`VALID`, `SUPERSEDED`, or `REVOKED`). | Enables third-party authenticity verification without exposing candidate email or full personal details. |
| 4.7 | Customizable Examination Workspace | clear | Server-persisted preferences (`users.preferences` JSONB via `/api/me/preferences`): font size, workspace theme (warm-paper, dark, high-contrast), navigator placement (side/bottom), layout (single question / scrolling paper), and timer style. | Persists accessibility and reading preferences across sessions without altering app chrome outside the exam. |
| 4.8 | Digital Scratchpad | incomplete | Private scratchpad drawer inside the exam workspace: text notes autosave to `attempts.scratchpad` (PostgreSQL, max 20,000 chars); freehand sketch canvas (pen/eraser, 3 inks, 2 widths, undo/redo) persists per attempt in `localStorage` and clears on submit. Never graded. | Keeps text notes portable across devices while avoiding large binary canvas blobs in the database. |
| 5.2 | Blueprint Difficulty Balancing (Innovation) | clear | Not implemented; scoped out in favor of complete delivery of Innovation 5.3 and Result Disputes. | Avoided half-built features; documented candidly as not implemented. |
| 5.3 | Failure-Resilient Examinations (Innovation) | contradictory | Brief requires both strict server deadlines ("no extra time") and recovery of offline answers. Resolved via IndexedDB local queue (`seq` + `capturedElapsedMs` anchored to `serverNow`) + bounded recovery window (`recovery_window_seconds`, default 120s, `0` disables) + plausibility check + `LATE_SYNC` tagging + examiner one-click discard. | Preserves legitimate work during brief outages without pausing the exam clock, while keeping every late-synced answer visible and discardable by the examiner. |
| 5.4 | Trust and Dispute Resolution (Innovation) | clear | Two-level dispute workflow (`016_disputes.sql`): candidate files within 7 days of publish (max 5/attempt) -> examiner resolves with rationale (optional 0.5-step written regrade) -> candidate accepts or escalates once within 7 days -> independent admin issues final decision. Append-only `dispute_events` timeline. | Gives candidates a transparent, accountable appeals process without letting a single party rewrite history. |
| 6 | Technical Constraints (Security, Validation, Integrity) | clear | Parameterized `pg` SQL (zero string interpolation), Zod validation on client and server, PostgreSQL `CHECK` and partial `UNIQUE` constraints, HTTP security headers (`nosniff`, `DENY`, `Referrer-Policy`), DB-backed rate limiting, and zero paid external APIs. | Defense in depth across browser, API, service, and database layers. |

## 4. Scope and Constraints

- **In scope**: End-to-end examination lifecycle for three roles, all 8 secondary features (4.1-4.8), Innovation 5.3 (Failure-Resilient Examinations), Trust and Dispute Resolution (Result Disputes), single-active-session enforcement, in-app notifications, submission receipts, append-only audit logging, and automated black-box verification (`scripts/verify.mjs`).
- **Out of scope**: Innovation 5.2 (blueprint difficulty balancing), SMTP email delivery, automated webcam/AI proctoring, real-time WebSocket push (polling/heartbeat is used intentionally for serverless compatibility), and paid third-party APIs.
- **Data constraint**: All seeded users, questions, exams, and results are fictional and simulated.

## 5. Risks and Mitigations

| Risk | Severity | Impact | Current Mitigation |
|---|---|---|---|
| Client-side clock or memory tampering during offline recovery window (Innovation 5.3) | Medium | A sophisticated candidate offline before the deadline could forge `capturedElapsedMs` before reconnecting within `recovery_window_seconds`. | Recovery window is bounded (`0..600s`, default `120s`, `0` disables for high-stakes exams); future-skew check (`+5s`); every late answer is tagged `synced_late = true`, logged as `LATE_SYNC`, highlighted in Grading, and discardable in one click. |
| Single-active-session lock on shared demo accounts (`409 SESSION_ACTIVE`) | Low | If a judge or script signs into a demo account that is still open in another browser within the 120s idle window, login returns `409`. | Clear error message explains how to sign out or wait 2 minutes; logout immediately releases the session slot. |
| Sketchpad canvas stored in `localStorage` only | Low | Freehand sketches do not roam across devices (unlike text notes in PostgreSQL). | Documented candidly; text scratchpad persists server-side in `attempts.scratchpad`. |
| Unautomated verification coverage for migrations `014`–`016` | Medium | `scripts/verify.mjs` covers slices `001`–`013` but does not yet include automated assertions for single-active-session (`014`), notifications (`015`), or disputes (`016`). | Type-checked, linted, and built via `npm run check`; documented transparently in `03-TRACEABILITY.md` as a known testing gap. |
